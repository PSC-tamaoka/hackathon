# Re:海学イベントプラットフォーム 仕様書

Oct 17, 2026 · @gen

## 1. 概要

「Re:海学」（仮称）は、岡山県渋川青年の家で「海の学校」などを体験した岡山県民を、イベントを通じてもう一度渋川へ呼び戻すスマホアプリ（iOS・Android）です。主催者がイベントを作り、経験者に招待を届け、当日は体験プログラムをスタンプラリーとして楽しめます。

### 背景

- 海事研修（通称「海の学校」）は、岡山県が70年以上前から続けている研修で、県内の小中学校約330校が毎年渋川海岸で実施しています（[KSB 2019](https://news.ksb.co.jp/article/13845395)、[KSB 2023](https://news.ksb.co.jp/article/14888993)）。
- 定番はカッターこぎ（長さ約9m・重さ約1.5tの船で約3km）と地引網です。
- つまり県内には、子どもの頃に渋川で同じ体験をした人が世代を超えて大勢います。この共通の思い出を、再訪と交流のきっかけにします。

### 目的

1. 渋川への再訪者（交流人口）を増やす
2. 経験者同士（同級生・親子・世代間）のつながりをつくる
3. カッター、地引網、海の生き物観察などの体験資源を、大人向け・親子向けに活かす

### 対象ユーザー

- 主対象：渋川青年の家の利用経験がある岡山県在住者（海の学校の参加経験者が中心）
- 副対象：その家族（親子参加）、イベントを企画する主催者（青年の家職員、地域団体、同窓会幹事など）

### 提供価値

| 対象 | 価値 |
| --- | --- |
| 参加者 | 思い出の体験を大人になってもう一度。同級生や同じ経験をした人と出会える |
| 主催者 | 経験者に絞って告知でき、申込から当日運営まで1つのアプリで完結する |
| 地域 | 来訪者が増え、渋川の魅力を再発信できる |

## 2. ユーザーロールと権限

ロールは「参加者・主催者・管理者」の3つです。イベントの作成は管理者（`users.is_admin` が true のユーザー）だけができ、作ったイベントの作成者が主催者になります。招待の乱用を防ぐため、招待の送信は1イベントにつき3回までとし、不適切なイベントは管理者が非表示にできます。

| ロール | 想定する人 | できること |
| --- | --- | --- |
| 参加者 | 渋川経験のある登録ユーザー | イベントの閲覧・申込・キャンセル、招待の受信、当日プランの確認、スタンプ獲得 |
| 主催者 | イベントを作った管理者（青年の家職員、地域団体など運営側） | イベントの作成・編集・中止、招待送信、参加者管理、当日の受付・スタンプ運用 |
| 管理者 | 運営チーム（ハッカソンでは自分たち） | イベントの作成・運営（主催者と同じ）、不適切なイベントの非表示、ユーザー管理、固定プラン（カッター・地引網など）の内容の更新 |

1人が複数ロールを持てる（主催者も参加者としてイベントに申し込める）ものとします。

### F-01・F-02 認証とプロフィール

- ログインはメールアドレス＋パスワード、またはGoogleアカウント。
- プロフィール：氏名、ニックネーム（他の参加者に見える名前）、メールアドレス、居住市町村、年代。
- 渋川経験（複数登録可）：参加年度、当時の学校名、学年、体験したプログラム、当時の立場（児童・生徒／引率教員／保護者など）。
- 渋川経験は自己申告とし、証明は求めません（仮置き）。招待の対象条件に使います。
- 通知設定：招待メールの受信可否、プッシュ通知の受信可否。

### F-03 イベント作成・編集（管理者・主催者）

| 項目 | 必須 | 内容・例 |
| --- | --- | --- |
| タイトル | ○ | 海の学校 同窓会 カッター＆地引網 |
| 説明文 | ○ | 内容、持ち物、服装 |
| カバー画像 |  | 1枚 |
| 開催日 | ○ | 時間は固定プランに合わせる（案では9:00〜15:30） |
| 集合場所 | ○ | 既定値は岡山県渋川青年の家（玉野市渋川二丁目7番1号） |
| 定員 | ○ | 人数 |
| 参加費 |  | 0円可。決済はアプリ外（当日現金など）とする |
| 申込締切 | ○ | 日時 |
| 対象条件 |  | 参加年度の範囲、当時の学校、年代、居住地域、親子参加可否 |
| 雨天時の扱い |  | 小雨決行／中止判断の時刻 |
| 公開状態 | ○ | 下書き／公開／締切／中止 |

- 当日のプランは固定プランが自動で付くため、主催者の入力は不要です。
- 「公開」にするとカレンダーに表示されます。「中止」にすると申込者全員に通知します（F-11）。

### F-04・F-05 カレンダー・詳細・参加申込

- ホーム画面は月表示のカレンダーです。イベント一覧画面は設けません。
- イベントがある日に印（ドット）を付け、受付中・満員・終了を色で区別します。
- 日付をタップすると、その日のイベントの詳細を開きます。同じ日に2件以上あるときは、画面下から出るシートでイベントを選んでから詳細を開きます。
- 月は左右のスワイプか矢印で切り替え、最初は今月を表示します。
- 自分の渋川経験が対象条件に合うイベントは、印の色を変えて目立たせます（Should）。
- 詳細：説明、開催日、地図、当日のプラン（固定）、残席、主催者名。
- 申込：参加人数（本人＋同伴者）、同伴者の年齢区分、連絡事項。完了後に確認メールを送ります。
- キャンセルは申込締切までマイページから可能。定員に達したら「満員」表示（キャンセル待ちはCould）。

### F-06・F-07 招待

1. 主催者がイベントの対象条件で対象者を抽出する
2. 対象人数と送信チャネル（メール／プッシュ／両方）を確認する
3. 招待文を編集する（テンプレートあり）
4. 送信する

- 送信先は、受信を許可した登録ユーザーだけです（オプトイン）。管理者なら誰でも送信できるため、送信は1イベントにつき3回までとします。
- 通知やメールのリンクから、アプリのイベント詳細を直接開きます（ディープリンク）。未ログインならログイン後にそのページへ戻します。
- 未登録の知人を誘えるよう、LINEなどに貼れるイベント共有URLを用意します（Should）。
- 招待ごとに送信数・開封数・申込数を記録し、主催者が確認できます（Should）。
- 配信の詳細は「6. 通知仕様」に記載します。

### F-08・F-09 固定プランとスタンプラリー

- ミッションは全イベント共通の固定とし、主催者による登録機能は設けません。項目・キーワード・曲の参照先はアプリ内固定とし、達成記録だけをDBに保存します。
- 実装は「カッター体験」「地引網体験」「海事研修の歌に関する体験」「仲間との集合写真」「当時の思い出を語り合う」の5つです。キーワードは順に「挑戦・協力・歌声・仲間・思い出」。下表は当日プランの参考案です。

| 時刻 | 内容 | スタンプ |
| --- | --- | --- |
| 9:00 | 受付・開会 | ○ |
| 9:30 | カッター | ○ |
| 11:30 | 昼食 |  |
| 13:00 | 地引網 | ○ |
| 14:30 | 海の生き物観察 | ○ |
| 15:30 | 閉会 |  |

- 参加者画面は「スタンプ台紙」として表示します。上にタイムテーブル、下に台紙のマスを並べます。
- スタンプは自己申告で押します。体験を終えた参加者が台紙のマスをタップし、「カッターを体験しましたか？」の確認で「押す」を選ぶと、押印アニメーションとともにマスに色が付きます。
- 達成操作・歌の利用はイベント開始時刻〜開催日の翌日いっぱい(日本時間)、かつ申込者だけです。サーバーでも参加資格と期間を確認し、同じマスは1回だけ保存して時刻を記録します。
- 主催者は申込者一覧で押印の状況を確認でき、押し忘れた人には手動で付与できます。
- 5つすべてを達成するとコンプリート演出と固定の「海事研修の歌」(YouTubeプレーヤー)を解放します。記念証画像とSNS共有はShouldです。

### F-10・F-11 主催者の運営機能

- 申込者一覧：氏名、人数、スタンプ進捗。CSV出力可。
- 当日受付：申込者一覧で名前を確認し、出席にチェック。
- 一斉連絡：前日リマインド、天候による中止・変更の連絡。

## 5. データモデル

主要テーブルは9個です。中心は「イベント（events）」で、申込と招待がそこにぶら下がります。固定プランは全イベント共通のマスタ（plan\_items）として持ちます。

| テーブル | 主な項目 | 関係・制約 |
| --- | --- | --- |
| users | id, email, name, nickname, city, age\_group, is\_admin, notify\_email, notify\_push | Supabase Auth のユーザーと1:1。is\_admin が true のユーザーだけがイベントを作り、作成者が主催者になる |
| shibukawa\_experiences | id, user\_id, year, school\_name, grade, role\_then, programs | users 1:N。role\_then は児童・生徒／教員／保護者 |
| events | id, organizer\_id, title, description, cover\_url, event\_date, place, capacity, fee, deadline, rain\_policy, status, is\_hidden, target\_conditions | status は draft / published / closed / canceled。カレンダーは event\_date で印を付ける。target\_conditions は年度範囲・学校・年代・地域・親子可をJSONで保持 |
| plan\_items | id, sort\_order, start\_time, title, place, stamp\_image, is\_stamp\_point | 固定プランのマスタ（全イベント共通）。初期データで投入し、アプリからは編集しない |
| registrations | id, event\_id, user\_id, party\_size, companions, status, note | (event\_id, user\_id) で一意。status は applied / canceled / attended |
| stamps | id, registration\_id, plan\_item\_id, stamped\_at, method | (registration\_id, plan\_item\_id) で一意＝二重押印なし。method は self（自己申告）/ manual（主催者が付与） |
| invitations | id, event\_id, sender\_id, channels, conditions\_snapshot, message, sent\_count, created\_at | 1イベントにつき3件まで。送信時点の対象条件を保存 |
| invitation\_deliveries | id, invitation\_id, user\_id, channel, status, sent\_at | status は sent / failed / opened / clicked |
| push\_tokens | id, user\_id, expo\_push\_token, platform, updated\_at | 端末ごとのExpoプッシュトークン。users 1:N |

申込数は registrations を数えて出し、残席＝capacity − 申込人数の合計とします。

## 6. 通知仕様

通知はメールとプッシュ通知の2チャネルで、5種類を送ります。招待は受信に同意したユーザーにだけ送り、すべての招待メールに配信停止リンクを入れます（特定電子メール法のオプトイン方式に沿う設計）。

| 通知 | タイミング | 宛先 | メール | プッシュ | 優先度 |
| --- | --- | --- | --- | --- | --- |
| 招待 | 主催者が送信したとき | 対象条件に合い、受信を許可した登録ユーザー | ○ | ○ | Must |
| 申込完了 | 申込の直後 | 申込者 | ○ |  | Must |
| キャンセル受付 | キャンセルの直後 | 申込者 | ○ |  | Should |
| 前日リマインド | 開催前日の18時 | 申込者 | ○ | ○ | Should |
| 中止・変更連絡 | 主催者が操作したとき | 申込者 | ○ | ○ | Should |

### メール

- Supabase Edge Functions からメール配信サービス（Resend）のAPIを呼んで送ります。
- 差出人名は「Re:海学」。件名例：「【招待】海の学校の仲間と、もう一度渋川の海へ」。
- 本文にはイベント名・日時・場所と、アプリのイベント詳細を開くボタン（ディープリンク）を入れます。
- フッターに配信停止リンクと運営者の連絡先を入れます。

### プッシュ通知（Expo）

- 通知の許可は、初回プロフィール登録の後に「なぜ通知が必要か」を説明する画面を挟んでから求めます。
- 許可されたら expo-notifications で Expo のプッシュトークンを取得し、push\_tokens に保存します。
- 送信は Supabase Edge Functions から Expo Push Service（Expoのプッシュ送信API）を呼んで行います。
- 通知の data に開きたい画面のURL（例：/events/123）を入れ、タップしたら Expo Router でイベント詳細を開きます。
- Androidでは、SDK 53以降の Expo Go でリモートのプッシュ通知を受け取れません。開発ビルド（development build）を作り、FirebaseのFCM認証情報を設定します（[Expo公式ドキュメント](https://docs.expo.dev/versions/latest/sdk/notifications)）。
- iPhoneで受け取るには、有料の Apple Developer Program のアカウントで開発ビルドとAPNsの設定が必要です。
- 送信結果で端末未登録（DeviceNotRegistered）のエラーが返ったトークンは、push\_tokens から削除します。

## 7. 非機能要件

重視するのは「海岸で、幅広い年代が、スマホで迷わず使えること」と「渋川経験という個人情報を外に出さないこと」の2点です。

| 分類 | 要件 |
| --- | --- |
| 対応端末 | iPhone・Androidのスマホアプリ（Expo）。主催者もアプリから操作する |
| 表示速度 | カレンダーと詳細は一般的な4G回線で3秒以内に表示（目標値） |
| 屋外での利用 | 日差しの下でも読める高コントラストと大きめのボタン。固定プランはアプリに同梱し、電波が弱くても台紙を表示できる。押印は通信が戻ってから送る（Should） |
| 使いやすさ | 利用者は20代から高齢者まで幅広い。本文16px以上、主要操作は3タップ以内 |
| セキュリティ | 通信はHTTPS。データの読み書きはSupabaseのRLSで本人・主催者に限定。ミッション達成はサーバー側で「開始時刻〜翌日いっぱい・申込者本人」を確認し、二重達成を防ぐ |
| 個人情報 | 学校名・参加年度・居住地は他の参加者に見せない。主催者が見られるのは申込者の氏名・人数・連絡事項のみ。登録時にプライバシーポリシーへの同意を取り、退会時にデータを削除 |
| 未成年 | 子どもは保護者の申込の「同伴者」として扱い、子ども単独のアカウントは作らない |
| 運用 | ハッカソンではSupabaseの無料枠で運用し、デモ用の初期データを用意する。アプリはストアに公開せず、開発ビルドを実機に入れて使う |

## 8. 技術構成

使用技術は TypeScript＋React Native＋Expo＋Supabase です。アプリはExpoで作り、サーバー側の処理はSupabase（データベース・認証・Edge Functions）にまとめるので、自前のサーバーは持ちません。

| 層 | 採用技術 | 用途 |
| --- | --- | --- |
| 言語 | TypeScript | アプリとEdge Functionsの両方 |
| アプリ | React Native＋Expo、Expo Router | 画面とナビゲーション、通知タップからの画面遷移 |
| カレンダー | react-native-calendars | 月表示と、イベントのある日の印（ドット） |
| 認証 | Supabase Auth | 1日版はメール＋パスワード |
| データベース | Supabase（PostgreSQL）＋RLS | 全テーブル。行単位で読み書きを制限 |
| サーバー処理 | Supabase Edge Functions | 招待の送信（回数制限）、メール・プッシュ通知の送信 |
| 押印の確認 | PostgreSQLの関数（RPCで呼ぶ） | 公開期間・本人・参加資格を確認して `rally_checks` に達成記録を保存 |
| 画像保存 | Supabase Storage | カバー画像、スタンプ絵柄 |
| メール送信 | Resend | 招待・申込完了メール |
| プッシュ通知 | expo-notifications＋Expo Push Service | 招待・リマインドの通知 |
| 定期実行 | Supabase Cron（Should） | 前日リマインド |
| ビルド | EAS Build（開発ビルド） | プッシュ通知を受け取れる実機用アプリ |

アプリから直接書き込むのは申込などの単純な操作だけにします。招待送信（回数制限）やスタンプ押印（当日・本人の確認）のように不正を防ぎたい処理は、Edge FunctionsかPostgreSQLの関数で行います。

## 9. ハッカソンでのMVPとデモシナリオ

開発は1日以内なので、MVPは「イベントを作る→招待する→申し込む→スタンプを押す」の一本道に絞ります。各機能は下の表の最小版で作り、Should以下は作りません。

### 1日版で作る範囲

| 機能 | 1日版での作り方 |
| --- | --- |
| F-01 ログイン | メール＋パスワードのみ（Googleログインはネイティブ側の設定が要るので省く） |
| F-02 プロフィール | 渋川経験は「参加年度」と「当時の学校名」の2項目だけ |
| F-03 イベント作成 | 対象条件は参加年度の範囲だけ。カバー画像は省略可 |
| F-04・F-05 カレンダー・申込 | 月カレンダー→日付タップ→詳細→申込。キャンセルは省く |
| F-06 招待メール | 文面はテンプレート固定。送信数の記録と3回の上限だけ |
| F-07 プッシュ通知 | 招待の1種類だけ。Androidの開発ビルドで受け取る。詰まったらメールだけでデモする |
| F-08・F-09 固定プランとスタンプ | 固定プランは初期データで投入。自己申告の押印、コンプリート画面 |

### 時間配分の目安（作業8時間と仮定）

1. 0:00〜1:00　土台：Expoプロジェクト作成、Supabaseのテーブルと初期データ（固定プラン、デモ用ユーザー20〜30人分の渋川経験）、ログイン
2. 1:00〜3:00　イベント作成、カレンダー、詳細、申込
3. 3:00〜4:30　スタンプ台紙と押印（デモの見せ場なので見た目に時間をかける）
4. 4:30〜6:30　招待メールとプッシュ通知
5. 6:30〜7:30　デモデータの仕上げと通し練習
6. 7:30〜8:00　予備（不具合対応）

3人以上のチームなら、2〜4を並行して進めます（画面担当、データ担当、通知担当）。開発ビルドは作成に時間がかかることがあるため、通知担当は最初の1時間でAndroidの開発ビルドとFCMの設定に着手しておきます。

### デモシナリオ（3〜5分）

1. 管理者アカウントでログインし、「海の学校 同窓会」イベントを作る（当日のプランは固定で自動的に付く）
2. 対象条件「参加年度2000〜2010年」で対象者を抽出し、招待を送る。参加者役のスマホにプッシュ通知とメールが届く
3. 参加者が通知をタップしてイベント詳細を開き、申し込む
4. ホームのカレンダーでイベントの日に印が付いていることを見せ、日付をタップして詳細が開くことを見せる
5. 当日画面でスタンプ台紙を開き、体験ごとにスタンプを押す
6. 全マスがそろい、コンプリート画面が出るところを見せる

デモ用の端末は、開発ビルドを入れたAndroidの実機にします。iPhoneでのプッシュ通知は有料のApple Developerアカウントが必要なため、1日版では見送ります。
